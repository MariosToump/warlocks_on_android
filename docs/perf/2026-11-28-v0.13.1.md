# Performance check 2026-11-28 (v0.13.1 + spell rework)

Why: a player on an Android 8 phone reports stutter "when the lava moves". The user wants steady FPS with no
visual change, and headroom for the coming 8-warlock mode.

## How it was measured
- **Stress run:** `scripts/perf_stress.gd`.
  - On the phone: tap the version label on the title screen 5 times. On the PC: `tools/perf_stress.gd`.
  - Endless fight with respawns. The lava shrinks every 7 s and regrows.
  - Every wizard is a bot holding two shop spells. Heat shimmer is on.
  - Two passes: 4 wizards, then 8 wizards, 90 s each.
  - Wall-clock frame times are split by lava phase (`wait` / `shrink`). The phone also logs `PERF` lines
    (`adb logcat -s godot`).
- **Device:** the user's phone. DN2103, Android 13, Dimensity 1200, Mali-G77 MC9, 2400x1080, 60 Hz, on USB power.
  - The Android 8 phone wasn't available. Its owner can run the same test (5 taps on the version) and send a
    screenshot of the results.
- **Before / after:** the same stress run in two builds.
  - Before: the old lava, AI and shader code.
  - After: the new code.
  - Raw logs are in `raw/`.
- **Targets:** steady 60 FPS, p99 under 20 ms, no frames over 33 ms in a normal fight, the last third within 10% of
  the first.

## Results on the phone

| Pass | Phase | 1% low FPS before → after | p99 ms before → after | Frames > 33 ms before → after |
|---|---|---|---|---|
| 4 wizards | lava waiting | 44.0 → 43.1 | 22.7 → 23.2 | 0.6% → 0.5% |
| 4 wizards | **lava creeping in** | **26.2 → 38.9** | **38.1 → 25.7** | **1.6% → 0.7%** |
| 8 wizards | lava waiting | 40.7 → 41.9 | 24.6 → 23.9 | 0.6% → 0.6% |
| 8 wizards | lava creeping in | 25.1 → 21.1 | 39.8 → 47.4 | 1.6% → 1.6% |

- **Average FPS** is 58.5-59.3 in every pass, and memory is flat (no leak).
- **One run each,** so the per-pass numbers are noisy.
  - The 8-wizard "after" pass had its bad frames in its first third. Its last third is 41 FPS 1% low, p99 24 ms.
  - The 4-wizard pass is the clean comparison.
- **The worst single frames** (171 ms before, 210 ms after) come in the first seconds. That's a first-use hitch
  (an effect's shader or texture loading), not the lava.

## What the PC measurements found (desktop CPU; an old phone is about 10x slower)

| Cost | Before | After |
|---|---|---|
| Lava edge step, every physics frame while it creeps in (`Arena._set_radius`) | 1.30 ms | 0.08 ms |
| Godot's tile update for one step (TileMapLayer chunks: 16 → 8) | 0.66 ms | 0.33 ms |
| Tile draw calls with the edge in view | 102 | 32 |
| Regrow, one frame at round start (script) | 7.2 ms | about 2 ms |
| One bot's think, 8 wizards | 180-450 µs | 140-210 µs |
| The "lava or about to be?" check the bots call hundreds of times (`is_unsafe`) | 1.9 µs | about 0.6 µs |

## Changes (no visual change)
Pixel-checked: the same arena frame after shrink → regrow → shrink with the old and new code. The diff is empty.

1. **The lava edge melts from a sorted list.** `arena.gd` `_melt_order` / `_melt_at`.
   - Each stone corner is sorted once by the radius at which it turns to lava.
   - A shrink step only touches the corners that actually melt, instead of testing about 4,000 every frame.
   - It only repaints cells next to a corner that changed.
2. **Regrow repaints only the cells the shrink touched** (`_dirty_cells`), not all 7,744.
3. **The TileMapLayer chunk size is 8** (`rendering_quadrant_size`; the default was 16). That halves the
   per-step tile rebuild and cuts tile draw calls about 3x.
4. **The bots use one merged check.** `Arena.is_unsafe(p)` replaces `is_lava_at(p) or is_lava_soon(p)`, with the
   same rule. In target picking, each candidate's lava check and opportunity score are worked out once per think.
   The bots' decisions are unchanged (the AI tests pass).
5. **The shaders skip work on stone pixels.**
   - `lava_glow`: stone pixels skip the five `sin()`.
   - `heat_haze`: stone pixels skip the second screen read.
   - The result is the same pixel, because mixing by 0 returned the original anyway.

## Top remaining problems (ranked by what a player feels)
1. **First-use hitches** of 100-200 ms in the first seconds of a match: shaders and effects are prepared the first
   time they're drawn.
   - Fix: warm them up behind the countdown (draw each effect once, off screen or at 0 alpha).
   - Size: small to medium.
2. **About 0.5% of frames over 33 ms in normal play,** even on this fast phone.
   - The cause isn't pinned down yet. Candidates: Android's own frame pacing, audio voices starting, or particles
     starting.
   - Next: log events next to the hitch frames.
   - Size: medium.
3. **8 wizards: the bots' thinking scales with wizard count squared** (each bot rates every other one).
   - It's fine on this phone, and about 2x cheaper now.
   - For 8-warlock mode on old phones, the next step is spreading thinks so no two bots think in the same frame.
   - Size: small.
4. **Heat shimmer costs one full-screen copy per frame.** It's the most likely GPU cost on an old phone, and the
   pause menu already has an Off switch.
   - Ask the Android 8 player to try the test with it off.
